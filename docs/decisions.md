## Known gaps (not fixed in M1)

- Between commits 3d07901 and 6fde61f (LAN sync S1, 2026-11-23) `cargo test -p health-core --test sync` fails: the seed list came before R6b (3bcba73). Bisecting across them needs that test skipped.
- One corrupt blob aborts `backup export` (use `--no-blobs`). Password strings aren't zeroized.
- The five-platform CI and release workflows have only been checked locally (macOS arm64). They run on the first push.
| 20 | Merge refuses new imports with a uid from the future (UUIDv7 time > now + 1 day), and non-UUIDv7 uids except on lab/staff/room sources (signed-result ids). It also refuses corrections whose HLC is from the future. Both are counted in the report | Security review: "larger uid / at wins" let a crafted backup take over local rows for good |
- Same-user limits of passphrase mode (plan §3.3), still open: `serve.json` is writable by the same user, so a same-user process can point the CLI at its own listener and collect the passphrase proof, or the passphrase on `health unlock`. The proof is static until the passphrase changes. This is documented, not fixed: no local design fully stops a same-user attacker.
- serve buffers up to 64 MiB of request body before checking auth, and unlock attempts queue behind a 1 s backoff, so another local user can slow the owner's unlock.
- Audit rows carry agent-supplied metric strings unbounded, record `rows = 1` for single-value writes, and skip revoked or expired tokens (they are refused before a grant is known).
- A source new to this device keeps the priority it had in the backup (as the web). A crafted backup could add a source that wins daily elections until the owner reorders it (Sources page).
- `derived.write` has no per-grant cap on metrics or imports beyond the 10,000 rows per call.
- `scripts/check-no-net.sh` and `cargo deny` cover the core workspace only. `gui/src-tauri` has its own lockfile and isn't checked yet.
- A second copy of the app (or a CLI `health serve` already running) leaves the window on "Starting the health core…" with the core's `running:` message; there is no single-instance handling yet.
- The OCR download against the real hosts was run by the owner on 2026-11-22 (the build agent's sandbox blocks network for freshly built binaries): all five files downloaded from Hugging Face and GitHub, matched their pinned hashes, and the installed models read a report (8 of 8 results preselected). Automated tests cover `health-connect` against a local server and the full install from a loopback mirror.
- One-click connect rewrites the agent's JSON with serde_json: numbers like `1e3` come back as `1000.0`. Values keep their meaning.
- A manual save with several entries is one import. If a later entry takes over only some of its rows and one of those is then removed, an older copy of that import (a backup, another device) can bring the removed value back. The GUI and `health add` save one entry at a time, so only `health op manual.enter` / the API can reach this.
- Long operations block: serve holds the profile while one op runs, so during a large import other calls wait; a forwarded CLI call gives up after 600 s and the GUI shell after 900 s while serve still finishes (and commits) the import.
- If computing `withheld` fails after a delegate write commits, the caller sees an error for a write that happened. Errors from the audit write itself aren't masked as `internal`. A failing `RELEASE` would leave a savepoint open (no known trigger).
- `cargo deny` isn't installed on the development machine and CI runs it for the core workspace only. The GUI shell's dependency licences were checked against `deny.toml`'s allow list from `cargo metadata` for macOS, Windows and Linux targets (all pass, 2026-11-22).
- The bundled core is signed ad hoc, so every new build is a new binary to the macOS keychain, which asks again before handing over the root key. A stable signing identity (release signing, M7) ends this.
- The desktop bundles have been built and smoke-tested on macOS only. Windows and Linux bundles first run in `gui.yml`. The first-run screen ("Create my health store") hasn't been clicked through in a real window: `health init` underneath is tested, the button wiring is not.
